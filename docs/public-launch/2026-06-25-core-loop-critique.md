# KALI — Core-loop critique (critic + fan) — 2026-06-25

## Verdict

KALI's foundations are genuinely strong — clean SkillExecutor, hardened SSRF defense, atomic rollback-safe deploys, honest "never a fake number" dashboards, careful local-privacy routing, working sticky-revoke consent — but the **entire create → use → share core loop is broken end-to-end by a chain of "created-but-inert" and "silent-failure" defects**, and every break is masked by a confident success message. A voice-built timed skill never gets a cron (wizard emits `interval` as free text, deployer reads `reminders.interval_hours`); even a correct cron fires `skill.{name}.trigger` into the void (zero subscribers); voice commands never execute tool calls (pipeline publishes `agent.response` and goes idle); newly built skills aren't re-discovered so the LLM can't see them; share/export only finds SKILL.md skills that the voice builder never produces; receiving a shared agent reports "installed" for a no-op; and onboarding's "create your first agent" fabricates success without ever calling deploy. The product demos as working because nothing ever says it failed — which is exactly why these are invisible in manual testing. This is fixable: the substrate (EventBus, Scheduler, sandbox, deploy rollback) is sound; what's missing is the wiring between layers and honest status propagation.

## Core-loop BLOCKERS (ranked)

### 1. Voice never executes tool calls — the action silently never runs
- **Surface:** chat-voice-routing / dashboard-widgets
- **Evidence:** `kernel/voice/pipeline.py:417-433` builds `tool_calls_payload` and publishes `Event(topic="agent.response", ...)` then `kernel/voice/pipeline.py:441` sets `IDLE` — no dispatch. Identical in `kernel/voice/remote_pipeline.py:189-218`. No Python subscriber to `agent.response` exists (only `ws_forwarder` at `kernel/main.py:452-458` forwards it to UI). The only tool executor is `_chat_logic` at `kernel/main.py:1404-1416`, which the voice path bypasses. Live by default: `kernel/models.py:171` sets `engine="python"` and `config/kali.yaml` doesn't override it.
- **User impact:** Every voice command requiring an agent ("добавь молоко в список", "запиши, потратил 500", "log my weight") does nothing. If the model also returns text the user *hears* "Готово" while nothing ran (broken promise); if it returns only a tool_use, the desktop `if response.text:` guard at `pipeline.py:438` makes it a total silent no-op. Voice is the headline input.
- **Fix-sketch:** In both pipelines, after `route()`, if `response.tool_calls` is set, dispatch through the existing (currently dead) `ToolDispatcher` at `app.state.tool_dispatcher` (`kernel/main.py:302`, auto-loads the agent), then run a second LLM pass to speak the real result — exactly like `_chat_logic` (`main.py:1418-1438`).

### 2. Scheduled skills fire into the void — `skill.{name}.trigger` has zero subscribers
- **Surface:** scheduler-proactive / skill-execution
- **Evidence:** Cron is registered to emit `skill.{name}.trigger` at `kernel/main.py:347` and `kernel/builder/deployer.py:65`. `kernel/scheduler.py:164` publishes it (`backend_preview.log:88` proves it fires live). But EventBus drops unmatched events (`kernel/event_bus.py:43,46`), and the only wildcard subscribers (`kernel/main.py:452-458`, `kernel/rust_bridge.py:35-43`) cover `{agent.*, voice.*, ui.*, dashboard.*, canvas.*, schedule.*, system.*}` — none match `skill.*`. `kernel/skill_executor.py` has no `.subscribe`. The spec (`docs/superpowers/specs/2026-04-13-kali-ai-os-design.md:121`) says "Scheduler emits skill.{name}.trigger → SkillExecutor handles it" — never implemented.
- **User impact:** Every reminder/monitor/notifier built "to run automatically" never fires. Deploy logs "Registered cron" (false success); restart re-registers the same dead topic.
- **Fix-sketch:** In lifespan, `event_bus.subscribe("skill.*", handler)` that parses the skill name from the topic, calls `skill_executor.execute(name, "check")`, and routes `should_fire`/alert results to NotificationManager + TTS. Also implement the planned `schedule.morning/evening` briefing subscriber.

### 3. Voice-built timed skills deploy with NO schedule — wizard emits `interval`, deployer reads `reminders.interval_hours`
- **Surface:** scheduler-proactive / voice-builder
- **Evidence:** Wizard maps "Как часто?" to flat key `interval` (`kernel/builder/wizard.py:138-139`); the LLM extractor uses the same flat key (`kernel/builder/extractor.py:50`). `_build_spec` writes it verbatim and `generate_skill` hard-sets top-level `schedule: config.get("schedule", None)` → None (`kernel/builder/skill_generator.py:96-97`). But `deployer.py:56-63` only registers cron from `config["reminders"]["interval_hours"]` or `config["schedule"]["cron"]` — neither ever produced → `if cron:` (`deployer.py:64`) always False. Startup re-registration has the identical mismatch (`kernel/main.py:339-344`). The value is raw text ("каждые 2 часа"), not an int, so it couldn't feed `f"0 */{interval_h} * * *"` even if read. The only test that passes hand-injects the nested shape the pipeline never produces (`tests/test_builder_deployer.py:39-47`).
- **User impact:** Even a *fully* answered voice reminder ("каждые 2 часа") deploys with zero schedule. Combined with #2, there is no path by which a voice-built timed skill ever fires.
- **Fix-sketch:** Normalize `interval`/`time_window` into `reminders.interval_hours`/`start_hour`/`end_hour` (or `schedule.cron`) in `_build_spec`/`generate_skill`; parse "каждые N часов" to an int. Cover with a test asserting `register_cron` is called for that request.

### 4. Onboarding "first agent" is never built or deployed — `start()` classifies only, then claims success
- **Surface:** onboarding-firstrun
- **Evidence:** `FirstAgentStep.tsx:29-33` calls only `builderApi.start(request)`, then `setState("ready")` + `setTimeout(advance, 1500)` — it never calls `builderApi.answer()` or `builderApi.deploy()` (the three calls in `builder.ts:61-66`). `BuilderFlow.start()` (`kernel/builder/flow.py:52-93`) only classifies + creates a wizard + returns the first question; deploy is a separate method (`flow.py:135-173`). The button renders "✓ Агент готов" (`FirstAgentStep.tsx:146`) after the WelcomeStep promised "Две минуты — и у тебя будет первый работающий агент". `FirstAgentStep.test.tsx:8-12` mocks ONLY `start`, confirming no other call exists.
- **User impact:** The single most important first-run moment produces zero agents while telling the user it succeeded. The whole loop opens with fabricated success and nothing to use or share.
- **Fix-sketch:** Drive the full flow in `FirstAgentStep`: after `start()`, loop `answer()` (auto-answer onboarding defaults or surface questions inline), then `deploy()`, and only show success after `{status:"deployed"}`. Surface real errors instead of a fixed success state.

### 5. Share/export is broken for exactly the agents voice creates — export only finds SKILL.md skills
- **Surface:** ugc-share-install
- **Evidence:** Export resolves via `SkillsRegistry` (`kernel/main.py:2080-2083`), whose `discover()` skips any dir lacking `SKILL.md` (`kernel/skills/registry.py:138-139`) and scans `skills/`, not `agents/`. The voice builder writes only `manifest.yaml` + `skill.yaml`, no SKILL.md (`kernel/builder/skill_generator.py:100-110`). The mobile share button shows for every `/agents` entry including manifest-only agents (`mobile/lib/presentation/agent_store_screen.dart:243-255`; `kernel/plugin_registry.py:168-181`).
- **User impact:** User voice-builds "water reminder" (headline use case), taps Share → "Не удалось подготовить агента" (`share_to_reels_screen.dart:212-217`). The create → share half of the loop is dead for the exact agents users make.
- **Fix-sketch:** Resolve export via `plugin_registry` (sees manifest agents) and synthesize a portable manifest/bundle for template agents; or generate a SKILL.md at build time so voice-built agents are first-class shareable.

## High

### Discover/registry gaps (created-but-inert)
- **`deploy_skill` never calls `plugin_registry.discover()`** — `kernel/builder/deployer.py:42-80` only does `skill_executor.load_skill` + cron; contrast `deploy_agent` at `deployer.py:107`. The shipping UI hits this (`ui/src/api/builder.ts:66` → `/builder/deploy`). The LLM palette is `plugin_registry.get_all_tools()` (`kernel/main.py:1381`) and dispatch keys on `plugin_registry.get(name)` (`main.py:1409`), so a just-built skill is absent from chat/voice until restart. Same gap in `/builder/create-skill` (`main.py:1672-1676`). *(This is known fix #1; flagged because the fix must land in `deployer.py` to also cover onboarding once #4 is fixed.)*
- **Imported shared agent never registered live** — `/skills/install-bundle` success branch calls only `_get_skills_registry().reload()` (`kernel/main.py:2058-2059`), a SkillsRegistry separate from the chat path; never `plugin_registry.discover()`/`skill_executor.load_skill`. `install_from_bundle` deploys to `%APPDATA%/KALI/skills` (`kernel/skills/installer.py:308`), which `plugin_registry` never scans. Contrast the `.kali-agent` path (`kernel/catalog/installer.py:90-101`). Receive-side of the loop produces an invocable-by-nobody skill.
- **Voice pipelines snapshot the tool palette once at startup** — `kernel/voice/pipeline.py:89` / `remote_pipeline.py:44` cache `self._tools = tools` from `get_all_tools()` evaluated once at `kernel/main.py:370,381`; no setter/refresh. Even after discover() is fixed, an agent added at runtime stays invisible to voice for the session. `/voice/start` only calls `start()`, not reconstruction — only a full app restart refreshes.

### Silent success / false confirmation
- **Import reports success on a functional no-op** — `mobile/lib/core/deep_link_service.dart:83-87` shows "Установлен ✓" on HTTP 200 + `status==ok`, which `kernel/main.py:2058-2065` returns as soon as files land, regardless of whether the agent is in `/agents`, loaded, or scheduled. This false signal is what hides every deeper break in manual testing.
- **UI deploy() reports success on a rolled-back deploy** — `deployer.py:47,77` return `{"status":"error"}` on rollback; route returns it verbatim as HTTP 200 (`main.py:1804-1805`); `postJson` only throws on `!r.ok` (`builder.ts:52-56`); store sets `phase:"done"` without checking `status` (`ui/src/stores/builder.ts:209-219`). Reachable on a fresh install with no LLM key (template=None → `load_skill` raises → rollback).
- **Voice deploy confirmation announces success on error** — `kernel/voice/pipeline.py:309-311` speaks "Готово! Агент {name} запущен" with no `result.get('status')` check; deployer error dict has no `name`, so it says "Готово! Агент  запущен" on failure. Live by default (`engine="python"`).
- **Failed model download still publishes `download_complete`** — `kernel/main.py:661-671`: on `if not success: break`, then unconditionally publishes `system.models.download_complete` with no error flag; `websocket.ts:76-80` advances onboarding regardless. The step then becomes unreachable (`completed` persisted) — no in-app retry. Hits the metered/poor-connection non-tech audience.

### Routing / dispatch
- **Chat dispatch doesn't auto-load → "is not loaded"** — `kernel/main.py:1416` calls `agent_runtime.dispatch(...)` which raises for unloaded agents (`runtime.py:116-118`); auto-load set is only `{system, weather, tasks, calendar, live-canvas}` (`main.py:485`). ~13 shipped native agents (email, news, currency, todoist, life-dashboard, etc.) trigger it on a clean install. The auto-loading `ToolDispatcher` exists but chat bypasses it; `/execute` lazy-loads (`main.py:1132-1134`), creating order-dependent flakiness. Dashboard tiles route through `/chat` (`Dashboard.tsx` → `ChatInput.tsx:130`), so clicking РАСХОДЫ/ЭНЕРГИЯ before the 30s poll loads life-dashboard returns "Error executing life-dashboard".
- **Local provider strips all tools** — `kernel/llm_router.py:366-391` (`_call_local`) never forwards `available_tools` and hardcodes `tool_calls=None`. Reached when `auto_route=false` (`:86-87`) OR — worse — on the first cloud failure, which sets `_cloud_available=False` (`:111`) permanently (never reset) and falls to local even with `auto_route=true`. "add to my list" silently degrades to a chat reply.

### Settings inert
- **LLM provider/model picker writes only to `os.environ`** — `POST /settings` (`kernel/main.py:2271,2259-2268`) sets env; the router reads from YAML config (`main.py:1384`, `llm_router.py:145`), which `ConfigManager.load()` parses only from `kali.yaml`. Switching OpenAI→Anthropic shows "Сохранено" but chat keeps using the old provider — even after restart (persists to `.env`, not YAML). Only the API *key* takes effect (SDKs read env), causing confusing auth errors. The correct YAML path (`api.updateConfig` / PATCH /config) is used by `VoiceSettings.tsx:90` but not the LLM picker.

### Trust / sandbox
- **Permission enforcer falls open for every `execute:*`** — `kernel/sandbox/permission_enforcer.py:10-17` METHOD_PERMISSIONS has no `execute` key; `can_execute` returns True when `required is None` (`:59-62`). `backend.py:147` builds `execute:{action}`, `runtime.py:122` uses bare `"execute"` — both unmapped → True. One (often implicit) approval authorizes all destructive actions including `calendar.delete_event` and `email/telegram` send. Tracked as ROADMAP 2.1 but breaks the trust loop.
- **Receiving device runs stranger code with no consent prompt / no disclosure** — `mobile/lib/core/deep_link_service.dart:72-81` POSTs the bundle with `overwrite:true` and no confirmation UI; the only gate is `safety_gate.check_code`, whose own docstring says it doesn't detect obfuscation and "targets naive code, not adversarial inputs" (`kernel/builder/safety_gate.py:195-198`). Because bundles drop `manifest.yaml`, `capabilities.py` has zero capabilities to disclose. The intended channel is a public TikTok/Reels link from a stranger — the riskiest path is the least gated. (RCE latent until skill execution is wired.)
- **Notifier "телеграм" channel offered, accepted, never delivers** — wizard offers it (`wizard.py:82`), but `NotifierTemplate._notify` (`kernel/skill_templates/notifier.py:60-81`) only appends to `history.json` and returns `{"status":"sent"}`; imports no Telegram client. Worse, it reads `config.get("default_channel","voice")` while the wizard stored `notify_channel`, so the chosen channel is ignored. Real Telegram delivery exists but only in the separate `agents/telegram/agent.py`.

## Medium / Low (grouped by pattern_class)

### created-but-inert
- **`POST /agents/create` writes to `agents/custom/` — never scanned, never loaded** (`kernel/agent_builder.py:17-19,134`; non-recursive `discover()` at `plugin_registry.py:156` skips it). Returns `{status:created}` for a permanently inert agent; doubly broken because runtime resolves `agents/<name>/agent.py`, not `agents/custom/<name>/agent.py`. Documented API surface (`README.md:72`, `docs/SETUP_GUIDE.md:202-214`). *Mitigation:* the shipped in-app builder uses `/builder/*`, not this endpoint. (Two near-duplicate findings cover this from the lifecycle and chat-routing angles.)

### dead-end-ux
- **"Done" screen tells user to invoke agent by name, but no affordance + skill not in palette** (`VoiceBuilderScreen.tsx:287-289`; only "Создать ещё" button). Builds on the discover() gap; the broken on-screen instruction is a distinct UX failure. Self-heals on restart.
- **АГЕНТЫ widget reads `agentStore` (live WS deltas only) not the `dashboardStore` the page fetches** (`AgentsWidget.tsx:4-5`; `setAgents` has zero callers; boot-time `agent.status.update` events lost — no WS backfill). Shows "0 онлайн / 0 зарег." on a healthy 5-agent system at every cold launch.
- **Mic-test "success" never arrives** — `MicTestStep.tsx:44-50` flips to success only on `transcript.length>0`, but the frontend listens for `voice.transcript` (`websocket.ts:55-56`) while every backend emits `voice.transcribed` (`pipeline.py:372`, `remote_pipeline.py:144`, Rust `state.rs:408`) — a name mismatch that drops the transcript for ALL speech/modes/languages, not just the wake word. Recoverable via the "Пропустить — только текст" skip button.

### silent-failure
- **`generate_skill` silently overwrites a same-slug skill** (`skill_generator.py:77,103-110`, `exists_ok=True`; no collision guard). The sibling UGC install path already implements the guard (`installer.py:341-345`), proving the voice-builder path is an asymmetric gap. Long-prefix slug collisions destroy a prior agent's config with a success message.
- **Tracker skill with `reminders:` registers a cron but tracker has no reminder action** (`agents/water-tracker/skill.yaml:1` + `:6-11`; `TrackerTemplate.execute` only log/summary/trend, `tracker.py:41-47`). The flagship example advertises reminders that can never fire — second face of the dead-trigger root cause.
- **Setting/rotating an API key never reaches a running agent** — telegram/messenger-hub/smart-home cache the token in `__init__` (`agents/telegram/agent.py:19-21`); `load_agent` early-returns when loaded (`runtime.py:67-69`); the "Работает" badge reads live env (`agent_keys.py:37`). Badge and capability disagree until restart. *(notion/todoist read env per-call, so they're fine — finding's scope was slightly broad.)*
- **Monitor template uses raw `urllib.urlopen`, bypassing the SSRF guard** (`kernel/skill_templates/monitor.py:111` with `# noqa: S310`; `url` is user/voice-supplied). Bypasses `http_client.py`'s private-IP block + whitelist + rate limiter. *Tempered:* the sandbox is documented as "not a security boundary against malicious code" — fix is to route templates THROUGH `SandboxHttpClient.for_agent`.
- **Notifier `notify` returns `status:'sent'` but only writes JSON** (`notifier.py:65-81`); LLM second pass then reports it as sent. Limited live exposure (no autonomous trigger wired); acknowledged as pending Proactive-KALI-v1 work.
- **LLM/voice dispatch bypasses SandboxBackend** — `main.py:1416` calls `agent_runtime.dispatch` directly (no rate limit, no audit_sink, no dry-run preview); those live only in `InProcessSandbox.dispatch` reached via `/agents/{name}/execute`. The M1.8 "Что делал Джарвис" audit under-reports the most common (chat/voice) actions. *Partial mitigation:* sticky-revoke (`can_execute(name,"execute")`) still applies.
- **Emptying an API-key field is a silent no-op** (`main.py:2246` truthiness guard skips empty strings; `_save_env` has no delete branch). Can't clear/revoke a key from the UI. *Low:* agent-key fields can't be cleared at all (canSave requires non-empty); no Remove affordance exists.

### broken-promise
- **Consent dialog is disclosure-only — "Не сейчас" leaves zero residue and first `/execute` auto-approves** (`ConsentDialog.tsx:7-8`; `_approve_agent(explicit=False)` at `main.py:1141`; sandbox fails open for unregistered agents `backend.py:148-158`). *Tempered:* this is the documented design (the real control is the working revoke button), and the LLM/voice path does NOT auto-approve — only the `/execute` REST endpoint does.

### silent-failure (not on a shipping trigger)
- **`RoutineManager.execute` reports every step "executed" while dispatching nothing** (`kernel/routines.py:88-102`; no `agent_runtime.dispatch`; no `routine.*` subscriber). *Low:* no create/delete endpoint, no UI, no LLM tool, no `routines.json` on disk — unreachable by any real user today.

## Crown jewels — protect these

- **Deploy rollback discipline** (`kernel/builder/deployer.py:42-77`): unloads + rmtree's on load OR fatal cron failure, treats an *invalid* cron as non-fatal ("skill still works on-demand"). Any discover()/schedule fix must preserve all-or-nothing-with-cleanup and invalid-cron-is-non-fatal.
- **`plugin_registry._is_callable`** (`kernel/plugin_registry.py:215-226`): deliberately withholds pure-SKILL.md skills (no `skill.yaml`) from the LLM palette so the model can't call a tool that returns "Skill not found". Don't loosen — instead ensure real skills have `skill.yaml`.
- **SSRF defense** (`kernel/sandbox/http_client.py`, `network_proxy.py`): `_resolves_to_private()` fails closed on unresolvable hosts; `_ValidatingRedirectHandler` re-checks whitelist + private-IP on every 30x hop. Route the monitor template through it rather than weakening it.
- **Scheduler + EventBus core** (`scheduler.py:104-105,170-171`; `event_bus.py:39-60`): croniter validation, crash-isolated loop, day-keyed de-dup, clean stop(); wildcard fnmatch dispatch with per-handler exception isolation. The substrate is right — only the `skill.*` subscriber is missing.
- **Honest empty states**: every dashboard widget degrades to "—" not a fake number (`SleepWidget.tsx:9-12`, mobile `/dashboard` `main.py:689-732` "never a fake number"); `ActivityWidget` pulls real audit records with an honest "Пока тихо". This is the discipline the success-message bugs violate — keep it.
- **No-silent-cloud-fallback** (`llm_router.py:86-87,121-129`): `auto_route=false` is honored and a local failure returns an explicit message instead of shipping text to cloud. Good privacy property — the gap is only that tools aren't carried into local.
- **Crash-safe config writes** (`config_manager.py:74-119`): tempfile + `os.replace` + fsync + `.bak`; PATCH /config validates against schema before writing. Route the LLM-picker fix THROUGH this path.
- **Honest key validation** (`/llm/test` `main.py:829-891`): real minimal request per provider before persisting; `ApiKeyStep` advances only after the backend confirms the write. Agent-key whitelist (`agent_keys.py:26-28`) + masked read-back guard prevent arbitrary env injection and mask-clobber.
- **`SkillExecutor` + `SkillTemplate` path-traversal guard** (`base.py:35-53`): blocks `..`/separators AND verifies `is_relative_to` after resolve. Bounded history, `KALI_TESTING`-gated mock status, sound reminder snooze/window logic — the on-demand contract works end-to-end.
- **Atomic bundle install + hardened extraction** (`kernel/skills/installer.py:168-190,310-361`; `tar.extractall(..., filter='data')` PEP 706). A failed import never destroys the previous version, and path-traversal/symlink attacks are blocked.
- **`useOnboardingGate`** (`useOnboardingGate.ts:26-52`): refuses to fall back to the wizard on a failed `/settings` fetch during the 40-60s cold ML boot; persisted `completed` flag skips splash for returning users. Don't "simplify" into a naive try/catch.
- **`runtime.py:127-136` non-sticky error status**: a per-call dispatch exception doesn't flip the agent to a permanent ERROR badge (hard-won fix for a prior bug). Preserve.
- **DispatchResult fail-safe contract** (`backend.py:174-206`): never leaks raw exceptions, always populates `duration_ms` + `denied_reason`, audits every branch. Preserve as skills/LLM paths fold into the sandbox.

## What we did NOT cover / gaps

- **Rust voice pipeline (`engine="rust"`)** — most findings are scoped to the default `engine="python"` path. The Rust pipeline (`src-tauri/.../pipeline.rs`) proxies to `/chat` and WOULD execute tools, but the cutover (Gate A) is pending. Once flipped, the python-path findings (#1, voice tool-snapshot) go inert but new Rust-path behaviors are unaudited.
- **Mobile (Flutter) client** beyond the share/import deep-link and agent-store list — chat correctness, voice WS round-trip, and offline behavior on real devices not deeply reviewed.
- **Multi-agent / concurrency** — no review of concurrent deploys, simultaneous voice + chat sessions, or EventBus backpressure under load.
- **Data persistence & migration** — per-agent JSON growth, `sandbox_audit.db` / `agent_consents` schema migration across versions, and skill-data isolation across overwrites not stress-tested.
- **LLM router fallback matrix** — only the local-tool-stripping and stuck-`_cloud_available` paths were traced; streaming wrappers, per-provider tool-format edge cases, and multi-provider failover ordering need their own pass.
- **Installer / distribution** — the prod-readiness audit (`docs/public-launch/2026-06-24-prod-readiness-audit.md`) covers signing/CORS/`0.0.0.0`/no-auth; this critique did not re-verify those and they remain the 4-blocker triage backlog.
- **Skills catalog / `SkillsRegistry` subsystem** as a whole — its relationship to `plugin_registry` is the root of several share/install findings and deserves a dedicated reconciliation (one registry vs two).
- **OpenWakeWord Russian accuracy** and the planned custom RU wake model — flagged in mic-test but not measured.
- **Accessibility, i18n completeness, and error-copy quality** across onboarding/builder screens not reviewed.
