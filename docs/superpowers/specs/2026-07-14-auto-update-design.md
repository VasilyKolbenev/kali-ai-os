# Auto-update для KALI Desktop (Windows) — Design

> **Дата:** 2026-07-14 · **Статус:** утверждён Vasily (подход A, полуавто-UX, GitHub Releases); ревью-исправления r2
> **Track:** dev-quality Track 4, приоритет №1. Спека → план (writing-plans) → TDD.

## Контекст и ограничения (почему не стоковый путь)

- Дистрибуция KALI = **InnoSetup DiskSpanning**: `KALI-Premium-Setup-<ver>.exe` + 3 `.bin`-слайса (~4,2 GB суммарно, слайс 2 000 000 000 байт). Tauri собирается `--no-bundle`; **tauri-plugin-updater не применим** — он требует собственную minisign-подпись и умеет ставить только NSIS (`/S`)/MSI-пакеты своего бандлера.
- kernel-код заморожен внутри PyInstaller-бандла → **почти любой значимый апдейт = полный ~4,2 GB**. Дельта-апдейты — вне скоупа v1 (см. Out of scope).
- Установка user-scope (`PrivilegesRequired=lowest`) → тихое обновление **без UAC**.
- EV-cert ещё нет (гейтится юрлицом): целостность в v1 обеспечивается **SHA-256 из манифеста, полученного по HTTPS с github.com** (якорь доверия). Minisign-подпись манифеста добавляется вместе с EV-флипом (записано в Out of scope).
- Хостинг v1 = **GitHub Releases** для ассетов (репо публичный; лимит 2 GiB/файл — слайсы влезают). **Манифест живёт в репо**, не в release-ассетах — см. «Данные» (причина: `releases/latest/` не отдаёт pre-release, а мы шипим `1.0.0-rc1`). Переезд на домен/CDN позже = смена одного base-URL.

## UX (полуавто, утверждено)

1. Апп проверяет версию при старте + каждые 24 ч (тихо; оффлайн/недоступный GitHub → молча пропустить).
2. Есть новая версия → ненавязчивый dismissible-баннер «Доступна KALI <ver>» с release notes и кнопкой «Скачать» (показать размер).
3. По клику — фоновое скачивание с суммарным прогрессом по 4 файлам; обрыв сети → баннер «Продолжить» (Range-докачка).
4. Все хэши сошлись → кнопка «Перезапустить и обновить» → тихий InnoSetup → апп перезапускается новой версией.
5. Никаких модалок и скачиваний без клика пользователя.

## Архитектура

| Компонент | Файл | Ответственность |
|---|---|---|
| Updater-модуль (Rust) | `src-tauri/src/updater.rs` | Команды `updater_check`, `updater_download`, `updater_install`; событие `updater://progress`; вся сетевая/файловая логика |
| Регистрация | `src-tauri/src/lib.rs` | invoke_handler + state; manifest-URL — const с override через env `KALI_UPDATE_URL` (тесты/будущий CDN) |
| UI-баннер | `ui/src/components/UpdateBanner.tsx` + слайс в Zustand | Состояния: `idle → available → downloading(%) → ready → installing → error` |
| Публикация | `scripts/publish_release.py` | Валидация версий → draft-релиз → ассеты → publish → коммит манифеста (порядок = защита от гонки, см. «Публикация») |
| Инсталятор | `scripts/installer_premium.iss` | +1 `[Run]`-строка перезапуска для silent-ветки + retry-ожидание завершения процессов в `[Code]` |

## Данные

**Манифест** — `releases/latest.json` в репо (raw URL: `https://raw.githubusercontent.com/VasilyKolbenev/kali-ai-os/main/releases/latest.json`); работает для pre-release-версий, а его коммит служит атомарным «флипом» публикации:

```json
{
  "version": "1.0.1",
  "pub_date": "2026-07-20T12:00:00Z",
  "notes": "Краткие release notes (RU)",
  "assets": [
    {"name": "KALI-Premium-Setup-1.0.1.exe", "url": "https://github.com/VasilyKolbenev/kali-ai-os/releases/download/v1.0.1/KALI-Premium-Setup-1.0.1.exe", "sha256": "...", "size": 123456},
    {"name": "KALI-Premium-Setup-1.0.1-1.bin", "url": "...", "sha256": "...", "size": 2000000000},
    {"name": "KALI-Premium-Setup-1.0.1-2.bin", "url": "...", "sha256": "...", "size": 2000000000},
    {"name": "KALI-Premium-Setup-1.0.1-3.bin", "url": "...", "sha256": "...", "size": 123456}
  ]
}
```

- `assets` перечисляет **все 4 файла с точными оригинальными именами**; загрузчик сохраняет по `name` из манифеста (НЕ из URL) — DiskSpanning Setup.exe требует слайсы с оригинальными именами в одной директории.
- Сравнение версий: semver с pre-release (`1.0.0-rc1 < 1.0.0 < 1.0.1`); текущая версия — `app.package_info().version` (источник — tauri.conf.json).
- Download-директория: `%LOCALAPPDATA%\KALI\updates\<version>\`.
- **Cleanup при старте аппа (stateless):** в `updates\` оставить только каталоги, чьё имя парсится как semver **строго новее** текущей версии аппа; всё остальное (включая непарсящиеся имена) удалить. Залоченные файлы (Setup.exe ещё дорабатывает после перезапуска) пропускать молча — доудалится при следующем старте.
- Резюм: файл существует и `len < size` → `Range: bytes=<len>-`; `len == size` → только верификация хэша; `len > size` → удалить и заново.
- Если во время скачивания N+1 очередной чек видит N+2 — игнорировать до завершения/сброса текущего цикла.
- Установка (`updater_install`): **повторная SHA-256-верификация всех файлов непосредственно перед запуском** (между ready и кликом могут пройти часы: антивирус, чистка диска) → spawn detached `Setup.exe /VERYSILENT /SUPPRESSMSGBOXES /NORESTART /LOG="<updates>\<version>\install.log" /DIR="<install_dir>"` → апп вызывает exit (лог внутри version-каталога — cleanup-правило владеет им однозначно; на первом пост-апдейт старте он lock-скипается и доудаляется позже). `<install_dir>` = родитель текущего exe (kali-desktop.exe лежит прямо в `{app}` — проверено); `/DIR` имеет приоритет над previous-dir, поэтому путь обязан быть точным.

## Инсталятор (.iss правки)

1. **Перезапуск после тихой установки:** новая `[Run]`-строка `Filename: "{app}\{#AppExe}"; Flags: nowait skipifnotsilent` — выполняется ТОЛЬКО в silent-режиме (существующая postinstall-строка с `skipifsilent` покрывает ручную установку; без флага новая строка запускала бы апп дважды при ручной установке).
2. **Гонка kill→copy:** сейчас `InitializeSetup` ждёт завершения только taskkill.exe, не release файловых хэндлов. Добавить после taskkill цикл ожидания исчезновения процессов `kali-desktop.exe`/`kali-backend.exe` (poll до ~10 с) — иначе file-in-use при копировании; `/SUPPRESSMSGBOXES` (выше) страхует от интерактивного Abort/Retry в «невидимом» апдейте. **Если процесс жив после таймаута** (юзер вручную перезапустил апп посреди апдейта): установка продолжается и авто-абортится на file-in-use — апп остаётся закрытым без перезапуска; принятый для v1 fail-режим, входит в E2E-перечень, ручной fallback = страница релиза.

## Публикация (`scripts/publish_release.py`)

Порядок обязателен (иначе окно битых апдейтов, пока 4,2 GB грузятся):
1. **Валидация единства версии**: tauri.conf.json (источник истины) == `#define AppVersion` в .iss == имена файлов в `dist_premium\installer\` == версия для манифеста; расхождение = hard-fail (иначе update-петля: апп обновился, считает себя старым, предлагает то же обновление).
2. `gh release create v<ver> --draft --prerelease` (флаг по наличию suffix) → upload 4 ассетов → `gh release edit --draft=false`.
3. Сгенерировать `releases/latest.json` (SHA-256 + size локальных файлов) → commit + push в main. **Коммит манифеста — последний шаг = атомарный флип**: клиенты не видят новую версию, пока все ассеты не опубликованы (raw-кэш ~5 мин задерживает только появление нового — безопасное направление).
4. **Идемпотентность:** при повторном запуске после падения — существующий draft той же версии переиспользовать/пересоздать (не плодить), уже загруженные ассеты перезалить.

## Ошибки

| Сценарий | Поведение |
|---|---|
| Чек не удался (оффлайн, 4xx/5xx, битый JSON) | Тихо пропустить, следующий чек по расписанию; лог в консоль |
| Мало места | Ошибка в баннере ДО скачивания, с числами. Порог: суммарный `size` × 2 — download 4,2 GB + Inno перезаписывает in-place с ~5,8 GB распакованного (пофайловый delta, пик < распакованного размера); ×2 — консервативная верхняя граница |
| Обрыв скачивания | Состояние `error` с кнопкой «Продолжить» → резюм с Range |
| SHA-256 не сошёлся (при скачивании или пред-инсталльной проверке) | Удалить битый файл, показать ошибку, retry скачивает заново |
| Инсталятор не запустился | Ошибка в баннере, ссылка на страницу релиза (ручной fallback) |

## Тестирование (TDD)

- **Rust** (`src-tauri/tests/updater.rs`, паттерн существующих tokio-тестов): semver-сравнение (rc-кейсы!), парсинг/отклонение манифеста, sha256-верификация, Range-резюм и повтор после обрыва, сохранение по `name` из манифеста, cleanup-правила — против локального axum-mock-сервера (без внешней сети → живёт в CI).
- **UI** (vitest): переходы состояний баннера, отображение прогресса/ошибок.
- **E2E-гейт (локальный)**: фейковый релиз (мелкие файлы + настоящий latest.json) на localhost, `KALI_UPDATE_URL` override → полный цикл до spawn инсталятора (инсталятор = стаб, фиксирующий аргументы, включая /VERYSILENT /SUPPRESSMSGBOXES /DIR).
- **Живой полноразмерный прогон** = обязательный шаг релизного ритуала (аналог frozen_smoke): предыдущая установленная версия обновляется на новую через опубликованный GH-релиз.

## Критерии готовности (Definition of Done)

1. Установленная старая версия детектит новый GH-релиз, качает с прогрессом, переживает обрыв сети (резюм), верифицирует SHA-256, тихо ставится и перезапускается новой версией — живой прогон.
2. `scripts/publish_release.py` публикует релиз одним вызовом (после существующего ритуала build → frozen_smoke), с валидацией версий и правильным порядком публикации.
3. Все гейты зелёные: cargo (включая новые тесты), vitest, kernel-suite не тронут; CI зелёный.
4. Оффлайн-старт аппа не показывает ни ошибок, ни задержек.

## Out of scope (v1)

- Minisign/подпись манифеста — вместе с EV-cert флипом (тогда же: подпись самих exe).
- Дельта-апдейты / разделение «лёгкий шелл + докачка паков» — направление EdgeAI-упаковки (§5 roadmap), отдельный проект.
- Каналы (beta/stable), автоскачивание без клика, macOS/Linux-апдейтер.
- Download-страница/CDN — отдельный трек дистрибуции; манифест-URL уже параметризован под переезд. **Известный риск v1:** raw.githubusercontent.com/GitHub эпизодически троттлится у RU-провайдеров (основная аудитория) — silent-skip деградирует мягко, но живой прогон стоит сделать и на потребительской RU-сети; переезд на CDN закрывает риск полностью.
