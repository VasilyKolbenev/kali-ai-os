# Jarvis 2026 — Personal AI Command Center

## Overview

A modern voice-controlled AI assistant and agent orchestrator inspired by the CLIK device concept. Jarvis 2026 transforms the original offline voice assistant into a full Personal AI Command Center — a hub for managing AI agents, life data, and smart home through voice.

**Target:** Desktop prototype (Tauri) with architecture ready for future embedded hardware (RPi).

## Goals

1. Voice-controlled AI agent orchestration — manage coding agents, life agents, smart home through natural speech
2. Life dashboard — sleep, tasks, calendar, spending, calories, habits displayed as widgets
3. Animated AI avatar — organic 3D blob (like CLIK) reflecting assistant state
4. Plugin system — community can build and share agents
5. Hybrid AI — cloud LLM (Claude) for complex tasks, local LLM (Ollama) as fallback
6. Hardware-ready architecture — kernel separable from UI for future RPi deployment

## Non-Goals (v1)

- Physical hardware design/manufacturing
- Mobile app (iOS/Android)
- Multi-user support
- End-to-end encryption between agents
- Offline-only operation (hybrid is the target)

### Component Details

#### 1. Python Kernel (FastAPI)

The kernel is the central process managing all subsystems.

**Event Bus:**
- In-process asyncio pub/sub for agent communication
- Topics: `voice.transcribed`, `agent.response`, `ui.update`, `system.alert`
- Agents subscribe to relevant topics and publish results
- Optional Redis backend for multi-process scenarios

**Scheduler:**
- Cron-like component that emits time-based events on the Event Bus
- Built-in events: `schedule.morning` (configurable, default 8am), `schedule.evening` (default 10pm), `schedule.hourly`
- Agents subscribe to these via `scheduled_events` in their manifest
- Config in `jarvis.yaml` for custom schedules

**Config Manager:**
- YAML-based configuration (`config/jarvis.yaml`)
- Hot-reload on file change
- Sections: voice, agents, llm, ui, integrations

**Plugin Registry:**
- Scans `agents/` directory for manifest files
- Tracks agent capabilities, permissions, health status
- Provides agent lookup by capability or intent

#### 2. Voice Pipeline

```
Mic -> Silero VAD -> OpenWakeWord -> faster-whisper -> LLM Router -> Agent -> Piper TTS -> Speaker
```

**Flow:**
1. Continuous audio capture from microphone
2. Silero VAD detects speech segments (filters silence)
3. OpenWakeWord listens for "Jarvis" trigger
4. On trigger: faster-whisper transcribes speech locally (~200ms)
5. Transcribed text sent to LLM Router
6. LLM determines intent via function calling, dispatches to agent
7. Agent response converted to speech via Piper TTS

**Voice modes:**
- **Wake word mode** — always listening for "Jarvis"
- **Push-to-talk mode** — keyboard shortcut or button press
- **Continuous mode** — always transcribing (for hands-free)

#### 3. LLM Router

Routes requests to the optimal LLM based on complexity and connectivity.

**Routing logic:**
- Simple commands (timer, volume, weather) -> local LLM (fast, offline)
- Complex reasoning (code review, planning, analysis) -> Claude API
- No internet -> local LLM fallback for everything
- User can force local/cloud per request

**Function calling:**
- Agent capabilities exposed as LLM tools/functions
- LLM picks the right agent and parameters
- Example: "Schedule a meeting with John tomorrow at 3pm" -> calendar.create_event(...)

#### 4. Agent Runtime

**Agent lifecycle:** Discovery -> Load -> Register -> Dispatch -> Execute -> Unload

**Agent manifest (YAML):**
```yaml
name: calendar
version: "1.0.0"
description: "Calendar & scheduling agent"
capabilities:
  - calendar.read
  - calendar.write
  - notifications.send
tools:                          # exposed to LLM as function calling tools
  - name: get_events
    description: "Get calendar events for a date range"
    parameters:
      date: { type: string, description: "Date in YYYY-MM-DD or 'today'" }
  - name: create_event
    description: "Create a new calendar event"
    parameters:
      title: { type: string }
      start: { type: string, description: "ISO datetime" }
      end: { type: string, description: "ISO datetime" }
scheduled_events:               # kernel scheduler emits these, agent subscribes
  - "schedule.morning"
  - "schedule.evening"
health_check: /health
protocol: native  # native | mcp | http
permissions:
  - network                    # needs internet for Google Calendar API
```

**Note:** Intent routing is LLM-based via function calling, not keyword matching. The `tools` field in the manifest is converted to LLM tool definitions. The LLM decides which agent to call based on the user's natural language request.

**Communication protocols:**
- **native** — stdin/stdout JSON-RPC (fastest, for built-in agents)
- **mcp** — Model Context Protocol (for Claude Code, Cursor-compatible agents)
- **http** — REST API (for heavy integrations: smart home, external APIs)

**Built-in agents (v1):**

| Agent | Purpose | Protocol | Integrations |
|-------|---------|----------|-------------|
| life-dashboard | Sleep, calories, spending, habits | native | Apple Health, Garmin, manual |
| calendar | Calendar management | native | Google Calendar, Outlook |
| tasks | Task/todo management | native | Todoist, Notion |
| smart-home | Home automation | http | Home Assistant |
| coding | Code agent bridge | mcp | Claude Code |
| system | System commands | native | OS APIs (volume, timer, music) |

#### 5. UI Shell (Tauri + React)

**Display modes:**

1. **Focus Mode** — fullscreen AI avatar + voice waveform (CLIK "Listening...")
2. **Dashboard Mode** — widget grid: sleep, tasks, calendar, spending, energy, agents
3. **Nightstand Mode** — clock, alarm, "Sleep well" greeting (CLIK nightstand)
4. **Agent Panel** — agent status list, logs, start/stop controls

**AI Avatar:**
- Three.js organic blob with procedural animation
- States: idle (slow pulse), listening (wave), thinking (spin), speaking (beat-sync)
- Color shifts: blue=normal, orange=warning, green=done, red=error
- Shader-based for smooth 60fps animation

**Dashboard widgets:**
- Sleep: hours + HRV score (fitness tracker integration)
- Next: upcoming calendar event with countdown
- Tasks: day progress (5/8 format with progress bar)
- Spent: daily spending total
- Energy: calories consumed/burned
- Agents: running agent count + status indicators

**Responsive layout:**
- Desktop: full dashboard with sidebar
- Compact: CLIK-like portrait layout (for future device screen)

## Interface Contracts

### Event Bus Message Envelope

```json
{
  "topic": "voice.transcribed",
  "source": "voice-pipeline",
  "timestamp": "2026-04-08T10:30:00Z",
  "correlation_id": "uuid-v4",
  "payload": { ... }
}
```

**Topic naming convention:** `{domain}.{action}` with optional `.{detail}`. Wildcard subscriptions supported (e.g., `agent.*`).

Core topics:
- `voice.transcribed`, `voice.wake_word`, `voice.state`
- `agent.request`, `agent.response`, `agent.status.update`, `agent.error`
- `ui.update`, `ui.command`
- `system.alert`, `system.shutdown`
- `schedule.morning`, `schedule.evening`, `schedule.hourly` (emitted by kernel scheduler)

### Agent JSON-RPC Methods (native protocol)

```json
// Kernel -> Agent
{"jsonrpc": "2.0", "method": "initialize", "params": {"config": {}}, "id": 1}
{"jsonrpc": "2.0", "method": "execute", "params": {"action": "get_events", "args": {"date": "today"}}, "id": 2}
{"jsonrpc": "2.0", "method": "health", "id": 3}
{"jsonrpc": "2.0", "method": "shutdown", "id": 4}

// Agent -> Kernel
{"jsonrpc": "2.0", "result": {"events": [...]}, "id": 2}
{"jsonrpc": "2.0", "result": {"status": "healthy", "uptime_s": 3600}, "id": 3}
```

### WebSocket Messages (Kernel <-> UI)

```typescript
type WSMessage =
  | { type: "voice.state"; state: "idle" | "listening" | "thinking" | "speaking" }
  | { type: "voice.transcript"; text: string; final: boolean }
  | { type: "agent.response"; agent: string; text: string; data?: unknown }
  | { type: "agent.status"; agents: AgentStatus[] }
  | { type: "dashboard.update"; widget: string; data: unknown }
  | { type: "error"; source: string; message: string; code?: string }
  | { type: "ui.command"; command: string; args?: unknown }  // UI -> Kernel
```

### LLM Router Request/Response

```python
@dataclass
class LLMRequest:
    text: str
    context: list[dict]       # conversation history
    available_tools: list[dict]  # agent capabilities as tools
    force_provider: str | None   # "cloud" | "local" | None (auto)

@dataclass
class LLMResponse:
    text: str
    tool_calls: list[ToolCall] | None
    provider_used: str         # which LLM handled it
    latency_ms: int
```

## Data Model & Persistence

SQLite database (`data/jarvis.db`) with the following entities:

**conversations** — voice interaction history (last 30 days, auto-pruned)
- id, timestamp, transcript, intent, agent, response, latency_ms

**agent_configs** — per-agent user settings and state
- agent_name, config_json, enabled, installed_at, updated_at

**dashboard_data** — widget data snapshots
- widget_name, data_json, source, timestamp

**user_preferences** — app-wide settings
- key, value_json

**On restart:** kernel loads agent_configs, re-discovers agents, restores last UI state from user_preferences. In-flight voice requests are dropped (stateless by design).

## Auth & Permissions

**API key management:**
- All API keys stored in `.env` file (gitignored)
- `.env.example` template with required keys listed
- Keys loaded via `python-dotenv` at startup

**External service auth (Google Calendar, etc.):**
- OAuth 2.0 flows handled by individual agents
- Tokens stored in OS keychain via `keyring` library (not in SQLite)
- Refresh tokens auto-rotated by agents

**Agent permission model (capability-based):**
- Manifest declares required capabilities (`calendar.read`, `fs.write`, etc.)
- On first agent load, kernel prompts user to approve permissions
- Approved permissions cached in agent_configs
- Built-in agents: auto-approved (trusted)
- Community agents: require explicit user approval per capability

**Agent sandboxing:**
- Agents run as subprocesses with no direct kernel access
- Communication only through defined protocols (JSON-RPC, MCP, HTTP)
- File system access limited to agent's own directory
- No network access unless manifest declares it

## LLM Routing Classification

The router determines provider based on two factors:

1. **Needs tool calling?** — if the intent requires calling an agent (calendar, tasks, etc.), route to Claude API (superior function calling). Local LLM only handles tool calls as fallback when offline.
2. **Simple response?** — if the request is conversational with no tool needs (greetings, time, basic math), route to local LLM for speed.

Decision flow: internet available? -> needs tools? -> Claude. No tools needed? -> local. No internet? -> local for everything.

## Data Flow Examples

### Voice Command: "Jarvis, what's my schedule today?"

1. OpenWakeWord detects "Jarvis"
2. faster-whisper transcribes: "what's my schedule today"
3. LLM Router -> Claude API (needs tool calling for calendar access)
4. Claude calls `calendar.get_events(date="today")`
5. Calendar agent fetches from Google Calendar API
6. Agent returns event list via Event Bus
7. Kernel formats response, sends to TTS
8. Piper TTS speaks: "You have 3 events today. First is Team call at 10am..."
9. UI updates: Dashboard shows highlighted events

### Agent Status Update

1. Coding agent (Claude Code) finishes a task
2. Agent publishes `agent.status.update` event
3. Event Bus routes to UI
4. WebSocket pushes update to frontend
5. Agent Panel shows green checkmark + completion message
6. Avatar briefly pulses green

## Graceful Shutdown

1. UI sends `system.shutdown` via WebSocket
2. Kernel publishes `system.shutdown` event on Event Bus
3. Each agent receives shutdown, saves state to agent_configs, closes connections
4. Voice pipeline stops audio capture
5. Kernel waits up to 5s for agents to finish, then force-kills remaining
6. SQLite connection closed
7. Tauri process exits

## Security Considerations

- API keys stored in environment variables, never in code
- Agent sandboxing — agents run in subprocesses with limited permissions
- Agent manifest declares required permissions, user approves on install
- All external API calls over HTTPS
- Input validation at every system boundary
- No eval/exec with user input
- Rate limiting on voice commands to prevent abuse

## Error Handling

- Voice pipeline: graceful degradation (STT fails -> retry, TTS fails -> text response)
- Agent crashes: automatic restart with exponential backoff, max 3 retries
- LLM unavailable: fallback to local model, notify user
- Network loss: switch to offline mode, queue cloud requests
- All errors logged with context (component, function, parameters)
